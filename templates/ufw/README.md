# UFW Example Configuration
Date: January 20, 2026

This directory contains the UFW artifacts that differ from the host defaults. It keeps only the files we actually change for the hardened IPv4-only stance described in `HardenUbuntu.md`. The files are intended for review and controlled copy into `/etc/ufw` as needed; they are not applied automatically.

## Selected configuration changes
The files reflect the following decisions and changes:

1) Incoming policy is default-deny; only required ingress is allowed.
2) SSH is allowed only on the administrative port `2222/tcp`.
3) HTTP/HTTPS ingress is restricted to Cloudflare IPv4 ranges on `80/tcp` and `443/tcp`.
4) IPv6 handling is disabled via the single-line change `IPV6=no` in `/etc/default/ufw` (documented in `HardenUbuntu.md`).

The Cloudflare allowlist is generated from `ufw.cloudflare` (which is itself generated by `scripts/cloudflare-ips.sh`). Re-run that script to refresh the IP ranges. If you want to update or create `templates/ufw/user.rules` in the same pass, run:
```bash
scripts/cloudflare-ips.sh --ufw
```

The `--ufw` option writes `user.rules` in the same directory as the allowlist file (whether you use the default output path or pass `--output`). It only replaces or creates the Cloudflare allowlist block and does not add SSH rules. Keep SSH entries in `user.rules` (or add them later when copying into `/etc/ufw/user.rules`) if needed.

UFW expects each rule line to be preceded by a `### tuple ###` comment. A practical explanation of why these comments matter (and how UFW rewrites rules without them) is here:
```
https://serverfault.com/questions/198398/how-to-add-an-iptables-rule-that-ufw-cant-create-in-ubuntu/980290#980290
```

The `--ufw` generator includes these tuple lines so UFW will preserve the ruleset on reloads. For background and format expectations, see the UFW configuration documentation:
```
https://manpages.ubuntu.com/manpages/jammy/en8/ufw-framework.8.html
```

## Current status on this host
As of January 20, 2026, this host is running UFW with default deny incoming, logging at the low level, and IPv6 disabled via `IPV6=no` in `/etc/default/ufw`. The active ruleset allows Cloudflare IPv4 ranges to ports 80 and 443 and includes the administrative SSH port `2222/tcp`. This reflects the policy described above and is consistent with the hardened IPv4-only stance described in `HardenUbuntu.md`.

## File map and intent
The retained files map directly to the UFW artifacts we actually change:

- `templates/ufw/user.rules` → `/etc/ufw/user.rules`
  - Includes only the allowed inbound rules (SSH 2222/tcp and Cloudflare IPv4 to 80/443) plus standard logging and rate limiting chains.

- `templates/ufw/ufw.cloudflare`
  - Source list of Cloudflare IPv4 ranges used to build the `user.rules` allowlist.
  - Regenerated by `scripts/cloudflare-ips.sh`.

- `templates/ufw/50-cloud-init.yaml`
  - Netplan template showing `dhcp6: no` and `accept-ra: no` for the hardened IPv4-only stance.
  - Apply by copying into `/etc/netplan/50-cloud-init.yaml`, then running `sudo netplan apply` and validating with `ip -6 addr show`.

## Notes on applying
When applying these examples:
- Ensure the SSH rule (port 2222) is in place before reloading UFW.
- If you adopt the Cloudflare allowlist approach, remove any broad `allow 80/tcp` and `allow 443/tcp` rules so direct-to-origin traffic is blocked.
- Ensure `/etc/default/ufw` has `IPV6=no` (one-line change) and reload UFW so the toggle takes effect.

## Open questions and next steps
The UFW posture is workable, but a few implementation choices should be settled so updates are repeatable. A clear decision on the refresh workflow reduces the risk of UFW rewriting the rules in an unexpected order.

- Decide whether Cloudflare allowlist refreshes should be applied by regenerating `templates/ufw/user.rules` and copying it into place, or by translating the allowlist into `ufw allow` commands. The former is file-driven; the latter is command-driven and preserves UFW-managed ordering.
- Document the routine for refreshing Cloudflare IPv4 ranges (for example, monthly or on-demand after a Cloudflare update) and the verification steps (`ufw status verbose`, targeted HTTP/S request checks).
- Confirm the preferred logging level once the new allowlist is stable so that recurring noise from blocked traffic is manageable without losing forensic value.
